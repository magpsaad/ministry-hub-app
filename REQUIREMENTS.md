# Youth Ministry Management App — Requirements Document

**Version 6 — multi-ministry (Project B, live in QA and production since 29 Sep 2026).** Changed or newly-added content in *this* revision is marked <span class="rev">like this</span> throughout (earlier rounds' highlighting has been cleared so this pass is easy to spot), and summarized in the Revision Log below. The full design record, with every decision and its reasoning, is `MULTI_TENANT_PLAN.md` (v4.1, approved).

**Purpose of this document:** This is a complete functional and technical specification for rebuilding an existing Google Apps Script / Google Sheets youth ministry management app as a modern, cloud-hosted, zero-cost web application. It is written to be pasted directly into a new Claude project as a build prompt. It documents both (a) the exact behavior of the current live app — so nothing is lost — and (b) a set of deliberate, agreed-upon improvements over that current behavior.

The current app is called **"St Arsanius Youth Ministry"** (short name "SAY Ministry"), used by a Coptic Orthodox church to track university/college-age youth ministry members, their attendance, outreach/pastoral care, volunteer ("servant") assignments, and a shared service calendar. It is being rebuilt so that (1) the same codebase/product can be reused by other ministries with different terminology (e.g. a high-school service), and (2) the underlying data store becomes a real relational database with near-real-time sync, instead of Google Sheets.

<span class="rev">This is a **multi-ministry deployment for one church**. One app deployment and one database (per environment) serve several ministries of the same church — University (SAY), and later High School, Junior High, Grade School/Sunday School and others. Each ministry has **its own web address**, its own settings, cohorts, members, servants, calendar and photos, and a **hard wall** between ministries: nobody working in one ministry can see or change another's data. Every ministry-owned row carries a 3-letter ministry code (`ministry_id`, e.g. `SAY`), and the database itself enforces the wall (§1.2). Other churches are out of scope: they would get their own schema or database. (Until v6 this document described a single-tenant deployment per ministry; that model was replaced by Project B, see §1.2.)</span>

## 1. Technology Stack

| Layer | Choice | Notes |
|---|---|---|
| Frontend | **Next.js (React) + Tailwind CSS** | Reproduce the existing visual design system exactly (see §8) using Tailwind utility classes/theme tokens |
| Backend / Database | **Supabase** — hosted Postgres | Relational database; replaces Google Sheets entirely |
| Realtime sync | **Supabase Realtime** (Postgres logical replication) | Near-instant updates across all connected users when any record changes |
| Auth | **Supabase Auth**, supporting **both** Google OAuth sign-in and email/password | Google sign-in is the default/primary path, matching current UX; email/password is a supported fallback |
| File storage | **Supabase Storage** | Member/servant photos, calendar attachments, QR code images, app logo — replacing the current Google Drive folder + filename-matching approach |
| Hosting | **Vercel**, free tier | Auto-deploys Next.js; free `*.vercel.app` subdomain to start (custom domain can be added later, ~$12–15/yr, decide later) |
| Row-level security | **Postgres RLS policies** | Enforces the role/group permission model (§4) at the database layer — see §4.4 |

All of the above operate comfortably within free tiers at this app's transaction volume and data size (see §9.3 for the storage-headroom analysis that confirms this).

### 1.1 Environments: Production and QA (corrected — single shared Supabase project, schema-separated)

**Correction from the previous revision**: Supabase's free-project limit (2 active projects) is **counted across your whole account** — every organization where you're an Owner/Admin shares the same 2-project cap, not 2-per-organization as previously stated here. Since you already have one active project elsewhere on your account, only **one** more free project slot is available in total. Two brand-new separate projects for this app's Production and QA (as originally proposed) would bring your account to 3 active projects, exceeding the free limit and requiring a paid plan for at least one of them. Apologies for the earlier inaccurate claim — corrected here with a source: [Supabase Billing FAQ](https://supabase.com/docs/guides/platform/billing-faq).

**Revised plan — one Supabase project, two schemas — fits entirely free:**
- **A single new Supabase project** for this app (your account's one remaining free slot), containing **two separate Postgres schemas**: `prod` and `qa`, each with its own full copy of every table (`groups`, `members`, `attendance_records`, etc.) — completely separate data, completely independent from one another, just sharing the same underlying project/database instance.
- **Storage**: separate Supabase Storage buckets per environment (e.g. `prod-photos` / `qa-photos`) within that one project — fully supported, no limit issue.
- **Auth**: Supabase Auth's user accounts are shared across the whole project (not schema-scoped) — which is actually convenient here: you and your testers sign in with the same account in both environments, and each environment's own `user_roles` table (living in its own schema) independently controls what that same person can do in `prod` vs. `qa`.
- **Still two separate Vercel deployments** (free, no limit concern there) — a production site and a QA site, each configured (via environment variables) to talk to its matching schema.
- New features/schema changes are built and verified against `qa` first, then the same migration is re-applied against `prod` once confirmed — same promotion workflow as originally planned, just routed through schemas instead of separate projects.

**Trade-off, stated plainly**: this gives genuine data separation (a QA mistake cannot touch `prod` rows — different tables entirely) but not full infrastructure separation — both environments share the same database compute and the same pool of login accounts. At this app's transaction volume, that's not a practical concern. If your other, unrelated Supabase project is ever retired or you're willing to pay for a second organization's Pro plan later, moving from schema-separation to fully separate projects is a straightforward one-time export/import — not a dead end, just not necessary today to stay at zero cost.

<span class="rev">**Addresses per environment (v6).** Each environment's Vercel project serves several web addresses, and each address belongs to one ministry or to the Church Admin console. The `qa` schema lists QA's addresses and `prod` lists production's (`ministry_addresses`), so QA and production can never mix. QA mirrors production exactly: a QA address per ministry and no ministry selector. Current addresses:

| | QA | Production |
|---|---|---|
| SAY | `youth-ministry-app-qa.vercel.app` (plus `localhost:3000` for local development) | `youth-ministry-app-prod.vercel.app` |
| Test Ministry (TST, QA only) | `test-ministry-qa.vercel.app` | – |
| Church Admin console | `church-console-qa.vercel.app` | `church-console-prod.vercel.app` |

Every address must also be listed exactly in Supabase *Authentication → URL Configuration → Redirect URLs* (QA and production share one list, since they share one project). Never use a broad pattern such as `*.vercel.app`. **Storage** keeps one set of buckets per environment (`{env}-photos`, `{env}-calendar`, `{env}-branding`), with **one folder per ministry** inside each (`SAY/members/…`, `SAY/profiles/…`, `SAY/calendar/…`, `SAY/branding/…`).</span>

### 1.2 Ministries: one deployment, a hard wall between ministries (new in v6)
<span class="rev">
**The rule.** Every ministry-owned row carries a `ministry_id`. A person can only read or write rows of the ministry whose address they are using, and only if they hold a role in it (or are the Church Admin). The rule is enforced in four independent layers:

| Layer | Mechanism | What it catches |
|---|---|---|
| Data integrity | Composite foreign keys, e.g. `members(ministry_id, group_id) → groups(ministry_id, id)` | A row pointing at another ministry's row can't be stored, whoever writes it (app bug, function bug, hand-written SQL, an import tool) |
| Security rules | Every rule on every ministry table requires `ministry_id = current ministry` **and** a role in that ministry | A forgotten filter in app code can never show another ministry's rows |
| Database functions | Each function takes the ministry from what it acts on (QR code, group, role grant) and scopes every statement to it | Functions that bypass the security rules by design |
| Application | The ministry is decided in one place, from the web address, and sent on every database call | Correct screens and counts |

**How the ministry is chosen.** The web address decides; there is no switcher and no combined view. The app looks the address up (`resolve_ministry_by_address`, cached for about a minute) and sends the ministry code with every database call in a request header (`x-ministry-id`). The header only **narrows**: every rule still requires a real role in that ministry, so faking it shows nothing. A request that names no ministry sees nothing (fail closed). Public check-in pages use the ministry of the scanned QR code instead. An **unknown address** shows "This address isn't set up"; an **inactive ministry** shows "This ministry isn't active" to everyone except the Church Admin.

**Per ministry vs church-wide.** 17 tables are per ministry (`app_settings`, `groups`, `members`, `universities`, `attendance_records`, `outreach_entries`, `service_calendar_events`, `holiday_rules`, `verses`, `qr_codes`, `pending_servants`, `pending_servant_attendance`, `audit_log`, `audit_config`, `actions_needed_config`, `user_roles`, `profiles`). Nothing is shared between ministries: verses and holiday rules can be *copied* into a new ministry when it is created, and the copies are independent. The only church-wide items are the login itself, the list of ministries (visible only in the console), and Release History / the app version (§6.16).

**Logins and profiles.** Supabase has one login system per project, so a person's login (Google identity, or email and password) is shared. Everything else is separate per ministry:
- Signing in on one ministry's address does **not** sign you in to another, and signing out of one doesn't sign you out of the other.
- A person has a **separate profile in each ministry** they serve in (name, phone, photo, gender, Father of Confession, join date, attendance and history), edited separately. Someone serving in two ministries fills in their details once per ministry.
- Merging duplicate accounts and "remove person" only ever act within the current ministry.

**Joining a ministry.** The person signs in on that ministry's address (a profile is created for that ministry), lands on its registration page (no ministry picker; one pending request per person per ministry), and that ministry's Admin approves them in Pending Servants. Alternatively an Admin can use **Add existing account by email** in Access Maintenance (§6.14).

**Church Admin.** A church-wide role held only by the owner (stored in `church_admins`, changed only by SQL). The Church Admin counts as an Admin of **whichever ministry's address they are on**, with full access to diagnose and fix problems, but still one ministry at a time; their actions are recorded in that ministry's audit log. Only the Church Admin can sign in to the console (§6.16), and only they can get into an inactive ministry.

**Adding a new ministry** (about 10 minutes, QA first):
1. **Vercel:** add the ministry's QA address to the QA project (and later its production address to the production project), under *Settings → Domains*.
2. **Supabase:** add each address exactly to the Redirect URLs.
3. **QA console → Create ministry:** 3-letter code (permanent, exactly A–Z, unique), name, address, first Admin(s) by email (the person must already have a login), labels, service weekday, timezone, cutoff time, proximity, sub-coordinator auto-servant, theme colour, and optionally copy verses and holiday rules from an existing ministry. This creates the settings row, audit switches, Actions Needed thresholds, the pre-entry group with its intake-only QR, the Servants QR, the address record and the first Admins' profiles and roles in one step.
4. Test it in QA; import its existing data with its own import tool (§10.3); then repeat step 3 in the **production** console with the owner's go-ahead.

If step 1 or 2 is missed, sign-in on that address fails with an error; nothing leaks. The design record and every decision's reasoning are in `MULTI_TENANT_PLAN.md`.
</span>

### 2.2 Groups, Cohorts, and the Ladder Position Model (revised)

Unlike the current app (which has 5 hardcoded, structurally-duplicated Google Sheets — one per year), **groups are rows in a database table**, not separate schemas. Each group represents a specific cohort of members, identified by an (optional but recommended) **cohort birth year**, plus a **ladder position** describing where that cohort currently sits in the progression. A group's *display name* can be generated automatically from a configurable template combining the cohort year and position — this is exactly how this deployment's "2007 Cohort - Yr 1 → 2007 Cohort - Yr 2" relabeling works: the cohort (the same real people) doesn't change identity when it transitions, only its ladder position advances, and its name is regenerated to match.

**This deployment's current ladder** (positions, not fixed group names — names shift every transition):

| Ladder position | Cohort year | Current display name | Accessible to |
|---|---|---|---|
| 0 (pre-entry) | 2008 | "2008 Cohort - Yr 0" | **Admin only** — hidden from everyone else, including General Coordinators |
| 1 | 2007 | "2007 Cohort - Yr 1" | Normal group access rules (§4) |
| 2 | 2006 | "2006 Cohort - Yr 2" | Normal group access rules |
| 3 | 2005 | "2005 Cohort - Yr 3" | Normal group access rules |
| 4 | 2004 | "2004 Cohort - Yr 4" | Normal group access rules |
| 5+ (terminal) | whichever cohort most recently arrived at Yr 4 | e.g. "2004 and earlier - Yr 5+" | Normal group access rules |

**How this works mechanically (revised during Phase G build, after three rounds of owner review):**
- Groups at positions 0-4 are each their own permanent row, keyed by `cohort_year`, exactly as originally designed — `ladder_position` is what the transition advances (0→1→2→3→4), and the display name regenerates from the template each time.
- **The terminal tier (Yr 5+) is a single, permanent group slot — not one row per graduated cohort — but the row occupying that slot changes hands every transition.** There is never a need to distinguish which original cohort a terminal member came from, not even for archiving — members leave the terminal tier one at a time, on a case-by-case basis, as they voluntarily stop attending; there is never a "whole cohort" archive action. (The only thing that might ever need filtering by original cohort in the future is a member's own `date_of_birth`, not the group they're in — not a current requirement.)
- **Yr 4's row *becomes* the new terminal row, exactly like every other position advances** (owner: "think of it as Yr 4 becomes Yr 5, just like all the younger years... it's the Yr 5+ cohort being added to the Yr 4," not the other way around) — same row, `ladder_position` set to 5, its own already-assigned `qr_color` left untouched. **Its display name is also left completely unchanged** (revised, migration 0033 — previously auto-regenerated as `"{its cohort_year} and earlier - Yr 5+"`; the owner pointed out a cohort's naming convention might look totally different by the time it's actually terminal, so nothing is assumed or generated — whatever name it already carries, set via Group Names' Rename control, simply continues unchanged). Its own Servants/Sub-Coordinators/Read-Only grants naturally stay attached — no reassignment needed, they just follow their row like any normal advance.
- **The row that *was* the terminal group before this transition is what gets absorbed and archived**: its members' `group_id` moves to the row that just became the new terminal, its own now-empty row is archived (not deleted, for history), and its own QR code is deleted (the new terminal row's own existing QR, just relabeled, is used going forward). **Its Servants/Sub-Coordinators/Read-Only grants roll back to the freshest incoming cohort instead** (the group that was position 0, becoming position 1 in this same transition) — they do not follow their (now-elsewhere) members into the new terminal row.
- **QR color**: Years 1-4 (and, per the above, the row becoming Yr 5+) all keep their own already-assigned color completely unchanged — this was already the existing rule and needed no special-casing once the merge direction was corrected. The brand-new incoming Yr 0 cohort inherits **the old terminal row's color, captured immediately before that row is archived** — i.e., each transition relays the outgoing terminal row's color one step down onto the new Yr 0.
- **First-transition caveat (owner-flagged, one-time only)**: since Yr 5+ has never been managed as its own distinct group with dedicated servants before this rebuild, whichever servants happen to be scoped to it going into the very first transition are somewhat arbitrary and will likely need manual cleanup regardless of the standing rule above — expected to be handled via the post-transition "Review Servant Assignments" step (§5), not special-cased in the transition logic itself.
- **Ladder position 0 is special**: it's a holding pen for members who haven't started at the group's normal entry point yet (in this deployment: high-schoolers not yet in university). It **does** get its own public, no-login QR code (§6.11, §6.15) — used at the ministry's annual welcoming party (July/August) to invite incoming members to submit their complete record information ahead of officially joining. That QR opens **intake only**: no "find your name and check in" option, since these individuals aren't tracked for attendance at this stage. Submissions go straight into this holding-pen group. Regardless of how a record gets in, this group is invisible to every other role — it appears in the side menu's group switcher for Admins only, no Sub-Coordinator/Servant/General-Coordinator role can be scoped to it, and only Admins can browse its roster.
- **Group naming**: `app_settings.group_name_template` holds a template string, e.g. `"{cohort_year} Cohort - Yr {position_label}"`, applied automatically whenever the transition trigger advances a cohort's position. A deployment that doesn't want cohort-year-based naming can simply leave `cohort_year` null on its groups and skip the template — names then stay exactly as manually set (e.g., a plain "Grade 9" style deployment).
- **New Yr-0 creation**: when the transition trigger runs and the current position-0 cohort advances to position 1, the process prompts the Admin to create the next incoming position-0 cohort (defaulting the suggested cohort year to "previous Yr 0's cohort year + 1," editable) — see §5.

## 3. Data Model

All entities below are Postgres tables. Column lists describe intent/type, not final SQL syntax — see the companion **DATABASE_SCHEMA.md** for the actual implementable DDL. <span class="rev">Every table in this section except `app_releases` also carries `ministry_id` (§1.2): uniqueness that used to be church-wide is now per ministry (cohort year, school name, role grants, a servant's one attendance per date, legacy import references), and every link between rows is a composite foreign key that includes `ministry_id`. Four church-wide tables support this and are not reachable through the API directly: `ministries` (code, name, active, display order), `ministry_addresses` (address → ministry, or `console`), `church_admins`, and `tenancy_settings` (the transition fallback, now NULL = fail closed).</span>

### 3.1 `app_settings`
<span class="rev">One row per ministry (primary key `ministry_id`; the old single-row `id` marker was dropped in migration 0066)</span> holding everything in §2.1 (including the school/field-of-focus labels and the proximity switches, migration 0059<span class="rev">; plus, from Project A, `theme_color`/`theme_color_light`/`theme_color_dark`, `servants_qr_color`, `my_assigned_header_color`(`_light`), `ladder_position_label` (e.g. "Yr") and `actions_needed_lookback_months` (default 12); and from Project B, `sub_coordinator_auto_servant` (default on, §4.1)</span>), plus `app_version` (text, e.g. "4.0"), `group_name_template` (text), `same_day_cutoff_time` (time, default 21:00), `timezone` (text, default "America/New_York"), and the "current service year" label used to generate QR code names dynamically (replacing the hardcoded `"25-26"` string in the current app).

### 3.2 `groups` (revised)
- `id`
- `cohort_year` (int, nullable) — the birth year (or other stable cohort identifier) this group represents
- `ladder_position` (smallint) — 0 = pre-entry/hidden, 1..N-1 = progressing, N = terminal
- `name` (text) — the display name; auto-regenerated from the template at transition time when `cohort_year` is set, otherwise manually managed
- `is_archived` (bool, default false) — true once this cohort has been fully archived out (§3.3.1)

### 3.3 `members` (replaces "Youth" / per-year "Master List")
One table for all members across all groups — no more one-sheet-per-year duplication.
- `id`
- `group_id` (FK → groups)
- `photo_url` (FK-style reference into Supabase Storage — **not** filename-matching like today)
- `full_name`
- `phone`
- `email`
- `university_college_id` (FK → `universities`) — *the field's label is the admin-editable `app_settings.university_label` (migration 0059), since a non-university service wouldn't call it "University/College"; likewise `program_label` for `program_of_study`*
- `program_of_study`
- `date_of_birth`
- `father_of_confession`
- `home_address`
- `is_visitor` (bool) — a visitor stays fully visible to servants everywhere in the app. Their attendance **is** now tracked and shown, tagged as "Visitor" (§6.5, §7.3) — this is a change from the original spec, which incorrectly excluded them from the Attendance tab entirely. They remain excluded from Dashboard aggregate stat counts and from the Actions Needed algorithm, matching today's behavior — flagged as an assumption in §12, confirm if this should change too.
- `gender`
- `comments` (member/registration comments, read-only after creation, matching current behavior)
- `assigned_servant_id` (FK → users, nullable)
- `servant_comments`
- `is_new_assignment` (bool) — notification flag, cleared when the assigned servant views/dismisses it
- `status` — `active` | `archived` (see §3.3.1)
- `created_at`, `updated_at`

**3.3.1 Archive vs. permanent delete:**
- **Archive**: available for members in a terminal-position group, individually or in batch, triggered explicitly by a Coordinator/Admin action (distinct from the yearly transition trigger). Archiving sets `status = 'archived'` — the member is removed from active rosters, dashboards, and stat counts, but their full record **and all historical attendance/outreach data are preserved** in the database, recoverable later. Confirmed: "if we ever run out of database space, we can delete them then" — archived rows are the long-term home for graduated members; permanent deletion is a separate, rare, manual DB-admin action outside the app's normal UI, not a feature to build.
- **Permanent delete**: a **General Coordinator/Admin** "delete member record" action (widened from Admin-only during Phase B build, per owner request — Servants never see this button, enforced both in the UI and at the database level), usable on a member in **any** group (not just a terminal one) — intended for correcting mistakes: a record entered in error, or a test record. This performs an actual irreversible delete and must require an explicit confirmation step. Confirmed: normal day-to-day removal from an active group does *not* happen — that's what the `is_visitor` flag is for (kept visible, excluded from stats). This permanent-delete tool exists specifically as a correction mechanism, not a routine "member left" workflow.

## 4. Roles & Permissions Model (refined)

This is a **deliberate redesign**, replacing the current app's confusing two-layer system (an app-level "Permissions" sheet allowlist *plus* independent native Google-Sheet sharing, with separate and easily-desynced "Serving Year" vs. "Access Year" concepts). The new model is simpler and enforced consistently.

### 4.1 Roles and their capabilities (capability split added)

- <span class="rev">**Church Admin** (v6) — church-wide, held only by the owner, and not a `user_roles` value (it lives in `church_admins`). Counts as an Admin of whichever ministry's address they are on (§1.2), is the only person who can use the Church Admin console (§6.16), and the only one who can get into an inactive ministry.</span>
- <span class="rev">**Every role below is per ministry**: a role grant belongs to one ministry and gives nothing in any other.</span>
- **Admin** — full access to everything, including admin-only screens (Access Maintenance, Universities Maintenance, Calendar Maintenance, Actions Needed Config, Audit Logs, Audit Report, Group Transition tool, Verses Maintenance).
- **General Coordinator** — full read/write access to **all groups'** member/attendance/outreach data, sees the Coordinator Corner, but not admin-only screens (unless also holding the Admin role). **Only General Coordinators (and Admins) can reassign a servant's serving group or remove a servant** via Servant Profiles & Assignments (§6.13).
- **Sub-Coordinator** — same data access as General Coordinator, but scoped to **exactly one group**. Can assign/unassign **members** to servants within their group (from the Dashboard's unassigned-members list or a member's detail view) — this is a normal part of managing group data. Sub-Coordinators **cannot** reassign a servant's own group or remove a servant — that stays General-Coordinator/Admin-only. **Assigning members to themselves**: since the assignment dropdown's semantics (caseload counts, gender filtering, "who's an active servant here") are inherently tied to holding the Servant role, a Sub-Coordinator who wants to personally take on members needs to also hold a Servant role row scoped to that same group — granted once via Access Maintenance, same as any other role grant (§4.2). This is expected to be a common, unremarkable combination. <span class="rev">By default this Servant row is added automatically whenever someone becomes a Sub-Coordinator; each ministry can switch that off on App Settings ("Sub-coordinators automatically become servants", `sub_coordinator_auto_servant`, default on).</span>
- **Servant** — the base role. Normally scoped to one group (their "serving group"), which determines: (a) which group's data they can view/edit, and (b) that they appear in that group's servant-assignment dropdowns. **"Unassigned" servant (confirmed during Phase C build, a legitimate permanent state, not just transitional)**: a servant role row may have no group at all — covers someone who's serving for a few weeks before a cohort decision is made, and equally a servant with a purely administrative function (marketing, food service, trips) who may never need cohort access at all. An Unassigned servant still passes as a general app user: Servants Directory, QR Codes, Service Calendar, and entering their own attendance are all available (gated by holding *any* role row, not a specific group) — but no cohort's actual member/attendance/outreach data is visible until a General Coordinator or Admin assigns them a group.
- **Read-Only (added, Phase F review)** — a fifth role value, always scoped to exactly one group, granting **view-only** access to that group's members/attendance/outreach (and its name/roster), with no write access at all and never appearing in that group's servant-assignment dropdown. This is the correct mechanism for the cross-group "exception access" case (§4.2) when the person must **not** be able to have members assigned to them or edit that cohort's records — distinct from the existing "grant an extra Sub-Coordinator row" pattern, which is full read/write. In practice this is always layered on top of a real primary role (e.g., a 2007 Cohort servant who also needs to just *look at* the 2005 Cohort) — it's not meant to be someone's only grant. <span class="rev">**Write controls are hidden for Read-Only (fixed in v6, QA R-1)**: attendance Present/Absent shows as plain text, and every "add outreach" entry point (Outreach tab, the youth record's New Outreach, the Dashboard's quick links and Follow-up card button) plus servant-assignment dropdowns are hidden. If a write is ever attempted anyway, the database still refuses it and the app shows a clear "You don't have permission…" message instead of a generic error.</span>

### 4.2 Multiple roles per user
A user can hold any combination of role rows, including the **same role type at more than one group** (§3.6) — this is how cross-group access exceptions (e.g., "a Year 1 servant who also needs Year 3 visibility") are handled: grant an additional role row scoped to the second group, through the same Access Maintenance screen used for everything else — full read/write via an extra Sub-Coordinator/Servant row, or view-only via the Read-Only role above, whichever the situation calls for. Effective access = the union of every role's group scope; effective capabilities = the union of every role's permissions.

### 4.3 Group transition and role scope
When the group-transition trigger fires (§5), **Sub-Coordinators and Servants scoped to a group move with their cohort** — their `group_id` follows the same underlying group row as it advances ladder position, exactly like a Servant's member assignments do. This holds for positions 1-4 *and* for the row advancing from 4 to the new terminal position — it's the same row throughout, so nothing needs to be reassigned. **Exception (revised during Phase G build)**: the row that *was* the terminal group before this transition is being absorbed and archived, not advanced — its own Servants/Sub-Coordinators/Read-Only grants do **not** follow their (now-elsewhere) members into the new terminal row; they roll back to the freshest incoming cohort (the group that was position 0, becoming position 1 in this same transition) instead. See §2.2/§5.

### 4.4 Enforcement
Enforce this entirely through **Postgres Row-Level Security policies**, keyed off `auth.uid()` joined against `user_roles`. This collapses the current app's fragile two-layer model into a single, consistently-enforced system — write the policy once per table, and it protects every query path, including future features. <span class="rev">Since v6 every policy also requires `ministry_id = current_ministry_id()` and a role **in that ministry** (§1.2). The group-access rules (members, attendance, outreach) work out the person's accessible groups once per query (`accessible_group_ids()`, migration 0067) rather than once per row, which keeps large lists fast.</span>

## 5. Group Transition (expanded)

- **Trigger**: a single explicit admin action ("Transition Groups" or similar), not automatic, not scheduled.
- **Effect of one click**: groups below the terminal position each simply advance in place (same row, `ladder_position` incremented, name regenerated from `group_name_template`). The row one below terminal **also just advances in place, to the terminal position** (§2.2, revised during Phase G build after three rounds of owner review) — same row, same color, **and its name is left completely unchanged** (revised again, migration 0033 — previously auto-regenerated with an aggregate pattern; the owner didn't want any naming formula assumed, since a cohort's display name might look nothing like a template-generated one by the time it's actually terminal). The row that *was* the terminal group is what's absorbed and archived: its members' `group_id` moves into the row that just became the new terminal, its own row is archived, its own QR code is deleted, and its Servants/Sub-Coordinators/Read-Only grants roll back to the freshest incoming cohort (§4.3) rather than following their (now-elsewhere) members.
- **QR color relay (added)**: Years 1-4, and the row becoming the new Yr 5+, all keep their own color completely unchanged. The brand-new Yr 0 cohort inherits the color of the row that *was* the terminal group, captured immediately before that row is archived (§2.2).
- **Atomicity / rollback**: the entire cascade (merge into terminal, every remaining group's position advance, role re-scoping, name/QR-label regeneration, new Yr 0 cohort creation) runs inside a single database transaction (`run_group_transition()`, migration 0028). If any step fails partway through, Postgres rolls back the whole operation automatically — the database is left exactly as it was before the trigger ran, with a clear error shown and nothing half-applied. This is a hard requirement, not an optimization.
- **New position-0 cohort**: as part of the same transition flow, the Admin is prompted to create the next incoming pre-entry cohort — a new `groups` row at ladder position 0, with a suggested `cohort_year` defaulting to "previous position-0 cohort's year + 1" (editable before confirming). This ensures there's always a place to keep entering next year's incoming pre-university members immediately after transition day.
- **Optional post-transition servant review**: immediately after the transition completes, present an optional, skippable "Review Servant Assignments" screen — every servant listed with a "keep current group / reassign" control, defaulting to no change. This reuses the existing single-servant reassignment function under the hood; it's just surfaced as a guided batch-review step right when it's most relevant, rather than requiring the Coordinator to revisit each servant individually later via Servant Profiles & Assignments (still available for anyone skipped or handled later).
- **Post-transition QR reminder**: since every group's display name changes with its ladder position, the transition flow ends with a prompt: "Group labels have changed — reprint QR codes for: [list of affected groups]," linking directly to the Print QR Codes view (§6.15). **Opens in a new tab** (owner-reported bug fix) — it's a full page navigation, not a modal, so following it in the same tab abandoned the completion screen entirely, losing access to the "Review Servant Assignments" option below it with no way back. Opening a new tab keeps the completion screen (and both of its follow-up actions) available regardless of which one is used first, or both.
- Log a `GROUP_TRANSITION_RUN` audit event.

### 6.11 New Member intake form (revised — see redesigned pipeline below)

**Full redesigned process, replacing the current QR-scan → Google Form → overnight batch-copy pipeline:**

Each group (and a separate one for Servants) has a QR code linking to a **public, no-login check-in page** scoped to that group — reachable at a stable, unguessable URL per group (`check_in_url` in `qr_codes`, §3.12). This is what gets printed and posted at the meeting, replacing the current Google Form link.

**Existing member flow**: scan the group's QR code → the check-in page shows a searchable list of that group's current active members → tap/select your name → submit → an `attendance_records` row is written **immediately, in real time**. No delay, no batch job — visible to servants instantly, same as walking attendance is recorded today via the Google Form, just without the separate spreadsheet hop.

**New member flow**: on the same check-in page, a "Don't see your name?" link leads straight into the New Member intake form — the same fields as the member schema (§3.3): Full Name, Phone, Email, University/Affiliation, Program, DOB, Father of Confession, Home Address, Gender, Comments. On submit: **the member record is created in the live roster immediately, AND today's attendance record is written for them, in the same operation** — both happen automatically and instantly. This fully replaces the current app's nightly Apps Script trigger (which copies "New Member Responses" rows into the Master List and back-fills their first attendance record hours later) with a real-time equivalent — new members and their first attendance show up for servants the moment they submit, not the next morning.

**Field validation (finalized during Phase C build)** — applies to both the member and servant self-registration forms: **Full Name, Phone, Email, and Gender are required**, listed first in that order (everything else stays free-form and optional). Full Name must contain at least two words; Phone must contain a valid North American digit count; Email must match a standard address shape. The submission is rejected (client-side immediately, and re-checked server-side regardless) until all four pass. **Phone numbers are auto-normalized on submit** to one consistent format, `1 (416) 930-1659`, regardless of how the person typed it in.

**Answering the process questions directly**: QR codes are printed via the Print QR Codes view (§6.15); scanning one opens the check-in page above (replacing the Google Form); and yes — a new member's information and their same-day attendance are both captured automatically and immediately, with no manual or overnight step involved.

**The position-0 pre-entry group** (§2.2) gets a variant of this same flow, not a manual-only one: it has its own public QR code, but scanning it opens **intake only** — there's no "find your name and check in" option, since these individuals aren't tracked for attendance yet. This is the QR used at the ministry's annual welcoming party (July/August) to capture incoming members' complete information ahead of them officially joining at the next Group Transition. Submissions land directly in the position-0 holding pen, visible only to Admins, with no attendance record written. (Admins can also add records here manually from the Admin Corner if needed, using the same form.)

**Servant self-check-in/registration (confirmed during Phase C build)**: the "Servants" QR code (§6.15) works exactly like a member group's QR — a shared, public, no-login page where an existing servant taps their name to check in instantly, or a new servant registers themselves the same way a new member does (name, phone, email, Father of Confession, gender, comments). The one deliberate difference: **self-registering does *not* create an app account.** A servant is always a real Supabase Auth account (they're the only role that ever logs into the app), and a public no-login page has no account to attach one to yet — so registering only captures the person's info and writes today's attendance, into a holding area (mirroring the position-0 pre-entry group's pattern, but for servants instead of members). An Admin or General Coordinator reviews and approves new registrations from a **Pending Servants** screen (Coordinator Corner). Approving doesn't immediately create an account either — it just clears them to get one. The **first time that real person actually signs into the app themselves** (ordinary Google/email sign-in, no special invite link), the app recognizes their email against the approved registration and automatically: creates their servant role as **Unassigned** (§4.1), copies their submitted contact info onto their new profile, and backfills every date they checked in while still pending into real attendance history — so nothing from before they had an account is lost. Someone who checks in again before being approved simply finds their own (still-pending) name in the list rather than submitting a duplicate registration.

## 7. Business Rules (exact logic to preserve)

### 7.1 "Actions Needed" algorithm (expanded to 3 card types)
The Dashboard's Actions Needed section (§6.3) merges three independently-computed card types into one per-servant card list, re-evaluated live on every render — nothing here is cached or requires a manual dismiss to "go away" except where noted.

**1. Outreach Needed** (amber, `lib/actions-needed.ts`) — for each active (non-archived, non-visitor) member, using the trailing 12 months of data:
1. Determine the member's `proximity` from their university/affiliation lookup (default `Unknown` if no match), and pull that proximity's thresholds from `actions_needed_config`. **If `app_settings.proximity_enabled` is false (§6.9), skip the lookup: every member is `Local` and the Local row is the only threshold set that applies.**
2. `presence_count` = count of attendance rows in the last 12 months.
3. `current_consecutive_absences` = walking backward from the most recent service date that has *any* attendance data recorded, count consecutive dates this member was absent, stopping at their most recent Present date.
4. `outreach_is_stale` = true if the member has zero outreach entries ever, or their most recent outreach `date_time` is older than `min_outreach_weeks × 7` days.
5. **Flag the member iff all three hold**: `presence_count >= min_presence_count AND current_consecutive_absences >= min_absence_weeks AND outreach_is_stale`.
6. **No manual dismiss** — the card is purely a live query result. It disappears on its own the moment the member attends again (resets their consecutive-absence streak to 0) or any servant logs a new outreach entry for them (resets staleness) — both simply change what the next render computes, with nothing to reset by hand.

**2. Newly Assigned** (blue, same card styling as New Registrations) — `members.is_new_assignment = true AND assigned_servant_id is not null`. Set to `true` by `assignServantAction` the moment a member is assigned a servant (previously a schema-only field nothing ever actually set); auto-cleared by a database trigger (`clear_new_assignment_on_outreach`, migration 0029, same code-path-independent pattern as the `join_date` trigger in §7.2) the instant any outreach entry is recorded for that member; can also be dismissed directly and persistently (`dismissNewAssignmentAction`) without requiring an outreach entry. Card shows the same info as a New Registrations card, plus "…has been assigned to you" in small text next to the name, an Outreach quick-link, and a Dismiss button.

**3. Follow-up Due** (mauve, distinct from the amber/blue above) — `outreach_entries` rows where `follow_up_due <= today AND follow_up_dismissed_at is null`, surfaced under the **entry's own creator** (`servant_id`), not necessarily the member's currently assigned servant — this is a personal reminder the servant set for themselves. Card shows the member's photo/name, "Your follow-up is due [date]," a **"View original entry"** link that opens the original entry **read-only** (`ViewOutreachEntryModal` — a reminder of what was noted, not an edit surface; editing stays on the Outreach tab, RLS-restricted to the entry's own creator), an **"Outreach" button** that opens the normal quick-outreach modal for that member and, on a successful save, **automatically dismisses this card** (no separate manual step needed once the follow-up is actually acted on), and a manual Dismiss button (sets `follow_up_dismissed_at`, keeping the entry itself intact as a record) for when no new entry is warranted.

All three respect "My Assigned List" (§6.2), filtering on each type's own relevant servant (`assigned_servant_id` for Outreach Needed/Newly Assigned, `servant_id` for Follow-up Due). Visitors are excluded from Outreach Needed (confirmed) — Newly Assigned and Follow-up Due are naturally scoped to whoever was actually assigned/outreached regardless of visitor status, since those are direct servant actions, not the trailing-12-months algorithm.

### 7.2 Attendance / "service date" logic (cutoff now configurable; Join Date + rolling windows added later)
- A date only "counts" as a real tracked service date if at least one attendance row exists for it anywhere in the group.
- **The same-day cutoff time (default 9 PM) and the timezone it's evaluated in are both configurable per deployment** (`app_settings.same_day_cutoff_time`, `app_settings.timezone`) — different ministries may run their weekly service on a different day and want the "don't show today until service is basically over" cutoff at a different hour.
- **Join Date (`members.join_date` / `profiles.join_date`, added)**: a person's earliest-ever attendance record, not the row's `created_at` (which is just when the database row was inserted -- for data brought over during migration, that would read as "everyone joined the day the migration ran," which is wrong). Maintained by a database trigger on `attendance_records` (fires on *every* insert regardless of which code path wrote it -- the internal Attendance tab, public QR check-in, new-member/servant intake, servant self-registration -- so it's automatically correct everywhere with nothing to keep in sync by hand); only ever moves earlier, never recalculated when a record is deleted. `null` until someone has attended at least once (e.g. the position-0 pre-entry holding pen, where no attendance is tracked at all). Shown as a read-only field on both Member Detail and Servant Detail.
- **Average attendance % = `present dates ÷ tracked dates in the rolling window`, floored at Join Date** — the window never reaches before the person's Join Date, whichever is later. The rolling window length is **admin-configurable, in weeks, independently for youths and servants** (`app_settings.youth_attendance_window_weeks` / `servant_attendance_window_weeks`, both starting at 52 -- owner's explicit choice, editable on the App Settings screen, §6.14). **Leaving either field blank means no rolling cap at all** — calculate over that group's entire attendance history since Join Date (migration 0027 made the columns nullable for this). This replaces the earlier all-time-since-registration rule for members and the hardcoded rolling-12-months rule for servants -- both are now the exact same formula, just with independently configurable (or disabled) window lengths, both floored at the real Join Date instead of `created_at`.
- **Only the configured service weekday counts toward this percentage** (owner-reported requirement) — for members and servants alike, both the "tracked dates" denominator and whether someone was "present" are restricted to dates falling on `app_settings.service_weekday` (Friday, ISO weekday 5, by default for this deployment; `lib/app-settings.ts`'s `isOnServiceWeekday()`). An attendance row recorded for an off-day special event (a retreat, a trip) stays fully visible everywhere else — the Attendance tab, Servants Attendance's date-picker, Member/Servant Detail's history — it just never moves this specific percentage, since it isn't a normal weekly service occurrence.
- **Stated on-screen everywhere this percentage appears** (added): the Member List, Servant Directory, and Servants Attendance screens each show a one-line caption naming the current rolling window and the configured day name (`lib/app-settings.ts`'s `weekdayName()`, kept in sync with the Service Day setting rather than hardcoding "Friday"), e.g. "Attendance % is a rolling trailing 52 weeks, counting only Fridays, never counting weeks before someone joined." The Member Detail/Servant Detail popups don't compute this percentage themselves (§6.4), so they carry no caption.

### 7.3 Visitor handling (reversed)
`is_visitor = true` members/rows: fully visible everywhere in the UI, **including the Attendance tab, where their attendance is now tracked and their row is tagged "Visitor"** (reversed from the original spec). They remain excluded from Dashboard aggregate stat counts and from the Actions Needed algorithm (confirmed).

The press-down feel took two attempts: round 1 added a no-op `touchstart` listener (the standard workaround for iOS Safari's `:active`-doesn't-fire-on-tap quirk) — owner still saw no movement on a real phone. Round 2 stopped depending on the `:active` pseudo-class at all: the root layout now delegates real `pointerdown`/`pointerup`/`pointercancel`/`pointerleave` events (one listener, `next/script`, covers every current and future button/link) to stamp `data-pressed="true"` on whichever button/link was actually touched, matched by a `[data-pressed="true"]` rule in `globals.css` (flat translateY + shadow-shrink, not per-color-family — the goal here is just "does it visibly move," not matching each family's exact resting alpha) plus a `-webkit-tap-highlight-color: transparent` reset so the browser's own default tap-flash doesn't mask it. Added a second, independent feedback channel that doesn't depend on seeing anything: real haptic buzz via the Web Vibration API (`navigator.vibrate(10)`) on tap, wired into the same delegated listener. **Hard platform limit, not fixable from this codebase**: the Vibration API works on Android (Chrome, Firefox, Samsung Internet, Edge) but Apple has never implemented it in WebKit on *any* iOS browser — an OS-level restriction. Feature-detected (`navigator.vibrate` checked before calling), so it's a silent no-op on iOS/desktop and only ever does something on Android. If the owner's phone is an iPhone, true tactile (vibration) feedback on tap is not achievable through a web app at all, full stop — only possible in a native app.
- **Small data visualizations** (built, Phase H, owner request): two hand-drawn SVG chart components (`components/charts/ProximityDonut.tsx`, `components/charts/AttendanceTrendChart.tsx`) — no charting library, consistent with the app's zero-dependency, hand-drawn-icon approach.
  - **Proximity donut**: **Analytics-only** (§6.7) — originally replaced the Local/Regional/Abroad/Unknown stat-card grid on the Dashboard *and* was added to Analytics, but the owner didn't want the same chart in two places, so it was pulled from the Dashboard entirely (§6.3) and kept only on Analytics, which didn't carry proximity data at all before this. Same four colors as the existing Proximity badges (§8's Badges spec: `#0c5460`/`#856404`/`#721c24`/`#383d41`) so the color already learned from badges elsewhere reads the same way here. Center shows the total count. A static legend with counts and percentages sits beside the ring — not hover-only, since hover doesn't reliably exist on the touch devices this app runs on. Handles the zero-members-yet case (empty gray ring) without dividing by zero.
  - **Attendance trend chart**: replaces the Analytics tab's Average Attendance by Month horizontal-bar list with an actual line/area trend chart (month-over-month, oldest-to-newest left to right) — a line is what actually reads as "trending up or down," which a per-month bar comparison doesn't. Value and month labels are drawn directly on the chart (not tooltip-only), month labels thin out automatically past 12 points, and the whole chart sits in a horizontally-scrolling container for groups with a long attendance history.
  - **Hydration gotcha found and fixed during build**: an SVG `<title>` tooltip written as multiple JSX expression children (`{a}: {b} ({c}%)`) hydrated with a server/client mismatch in testing; rewritten as a single template-literal string child, which resolved it. Also switched the trend chart's month-label formatting from `toLocaleDateString(undefined, ...)` to a hand-written month-abbreviation table, since resolving against the runtime's *unspecified* default locale is exactly the kind of thing that can differ between Node (SSR) and the browser (hydration).
- **Dark mode — parked, not in this build.** May be added in a future version at the owner's request.

## 10. Data Migration (fully specified)

### 10.1 Incremental refresh during the testing period (one-way — Sheets is sole source of truth)

Confirmed: the current Google Sheets app remains the **only** source of truth for real data throughout the testing window — the new app is for navigation/functionality testing only, and anything you create there directly is disposable, not data of record. This is a **one-way sync**, with a rule to handle throwaway test data cleanly, and — as of v5 — a broadened set of tables excluded from the ongoing sweep so that admin configuration work done in the new app isn't overwritten each refresh.

**Operational tables — wipe-and-reload on every refresh (simplified from the original insert/update/delete-diff design during Phase I planning, owner's explicit instruction)**: these have real, ongoing Sheets activity throughout the testing window (servants keep using the old app), so each refresh makes them an exact mirror of current Sheets content: `members`, `attendance_records`, `outreach_entries`, `service_calendar_events`, and `audit_log` (added to this list during Phase I planning — see MIGRATION_PLAN.md §3.10/§4).

1. Read the current state of the corresponding sheet/tab via the Sheets API.
2. Clear the table (scoped to whichever schema — `qa`/`prod` — the run targets).
3. Insert every current Sheets row fresh, tagged with `legacy_source_ref` for traceability.

This is simpler than the originally-specified diff-based sync (no insert/update/delete branching to get right) and has the same net effect for these tables: after a refresh, the new app is an exact mirror of current Sheets content, and any row created directly in the new app while testing (no Sheets origin) is gone. See MIGRATION_PLAN.md for the full design, per-table field mapping, and every data-quality decision made against the real source data.

**Configuration tables — excluded from the ongoing sweep.** These are admin-curated settings, each with its own maintenance screen in the new app (§6.14, §6.9, §6.1): `universities`, `verses`, `audit_config` — plus the already-excluded `user_roles`, `app_settings`, `groups`, and `qr_codes` (§4.2 covers `user_roles` specifically). These are **seeded once from their current Sheets values during the initial migration**, but after that, they're owned entirely by the new app's own admin screens and are never touched by a subsequent refresh — so if you add a university or edit the verse list directly in the new app while testing, a refresh will never undo that. The trade-off, stated plainly: a genuinely new university or verse added on the *Sheets* side after initial migration won't automatically appear in the new app via refresh — it would need to be added directly through the new app's own maintenance screen instead, since these are now admin-owned configuration rather than ongoing synced data. **`actions_needed_config` is excluded even from the initial seed (revised during Phase I planning, owner's explicit instruction)** — unlike the others, this one was never migrated from Sheets at all; the owner configured its thresholds directly in the new app, and the migration tool never touches this table, in either direction.

**Role assignments** (`user_roles` — who is an Admin/General Coordinator/Sub-Coordinator/Servant, and for which group): the old Permissions sheet doesn't map cleanly onto the new role model (§4), so these are set up once, directly in the new app's Access Maintenance screen, and are expected to diverge from (and eventually fully replace) the old sheet.

**Existing servants need real accounts pre-created during migration (added, Phase F review; decided during Phase I planning)**: Access Maintenance can only grant a role to a `profiles` row that already exists, which itself only gets created lazily on that person's first real sign-in (§6.1's Phase A design) — there's no account yet to attach a role to otherwise. Decided: the migration tool **pre-provisions** a real `auth.users` row (via Supabase's admin API, email pre-confirmed, no password set — this does not send any email; only the separate invite/reset-password calls do, and neither is used) plus a matching `profiles` row and every `user_roles` grant, for every person in the old Permissions sheet, keyed by email — not just a checklist. Idempotent: re-running never deletes or recreates an existing account. **Role mapping** (the old Permissions sheet's `admin`/`coordinator`/`servant` doesn't distinguish General from Sub-Coordinator, and its per-group `Access Year N` columns needed a rule for people with more than one): see MIGRATION_PLAN.md §3.5 for the full validated mapping (which specific 3 people are General Coordinators, and the "extra access years beyond your one real Serving Year become Read-Only grants" rule, verified against the source spreadsheet's actual cell highlighting, not just described).

**Phone number normalization (confirmed during Phase C build)**: every phone number brought over from Sheets during migration must be reformatted to the same standard the app itself now enforces on new entries (§6.11 item 6) — `1 (416) 930-1659` — regardless of whatever format it's stored as in the source sheet, so the whole roster is consistent from day one rather than only new registrations being clean.

**Join Date needs no special migration handling (confirmed, §7.2)**: as long as the migration tool inserts each person's real historical `attendance_records` rows with their true original `service_date` values (which it already needs to do to preserve attendance history at all), the `join_date` trigger fires on each insert and automatically converges on the correct earliest date -- no separate "set join_date" step, no extra migration logic. This only works if attendance rows are inserted with their real historical dates rather than the migration run's date.

`groups` and `qr_codes` are new-app concepts with no Sheets equivalent at all — neither is touched by a refresh; they evolve only through the app's own tools (Group Transition, Admin settings). **`audit_log` was originally scoped the same way (new-app-only, never a mirror of anything) but is now migrated and refreshed** (revised during Phase I planning, owner's explicit instruction) — see MIGRATION_PLAN.md §3.10 for the old→new action-type mapping and the new `legacy_source_ref` column migration 0034 adds to support it.

### 10.2 Production Cutover Runbook

Target: the weekend following the last Friday meeting of the Coptic year, **September 11, 2026**.

1. Freeze the Google Apps Script app (no further edits accepted).
2. Notify current app users not to attempt any changes during the cutover window.
3. Run one final data migration — either another incremental refresh, or a full fresh reload, at your discretion at the time.
4. Once that final migration is confirmed complete, trigger the annual Group Transition in the new app to confirm the whole mechanism (§5) works correctly end-to-end on real data.
5. Send the new app's link to all users.
6. Users log into the new app and begin normal use; the old Google Sheets app is retired.

**QA doesn't get retired or paused at cutover.** Owner-confirmed: `qa` stays live indefinitely afterward as the ongoing pre-Production testing ground for future work, same as before cutover — the corrected `qa`-first-then-explicit-promotion workflow (§13) keeps applying, it just matters more once Production has real users on it. **A handful of real servants have (and keep) `qa` access to help test** future changes before they're promoted, alongside the owner — not just the owner testing alone. Since `qa` and Production are two different websites sharing one login system (§1.1), a servant with access to both needs a way to tell them apart at a glance: **the QA deployment shows a permanent, impossible-to-miss bright-orange banner** ("QA Testing Environment — Not the Real App," `web/src/app/layout.tsx`, env-gated on `NEXT_PUBLIC_APP_ENV`) at the top of every screen, never shown on Production. **Removing a servant's access (or a whole account grant) in `qa` never touches Production** — every access-management action in the app (Access Maintenance, Pending Servants, `remove_servant` and every other role RPC) only ever writes to schema-scoped tables (`user_roles`, `members`, `profiles`), never to the shared `auth.users` login table itself, so `qa` and Production access are safely independent to edit.

### 10.3 The Sheets tool is retired; rules for future per-ministry imports (new in v6)
<span class="rev">
SAY's cutover is complete, so the one-way Sheets refresh tool (§10.1) is **retired**: it has a hard stop so it can't run (it wiped whole tables and the photo bucket, which would now destroy data) and is kept only as a reference. **Each new ministry will need its own one-time import tool before it launches.** Every such tool must:
1. Target exactly one ministry, named by its code, and refuse to run without it.
2. Never delete or truncate anything. Insert only; a re-run must first check the ministry is still empty and refuse otherwise.
3. Run in QA first (dry run, then real run), be checked by that ministry's testers, and only then run in production with the owner's explicit go-ahead.
4. Write photos only under that ministry's folder.
5. Produce a report of rows read, inserted and skipped (with reasons) for the owner to review.
6. Rely on the database's cross-ministry protections (§1.2) as a safety net, never as the plan.
</span>

## 13. Working Agreement for This Project (versioning workflow added)

Whenever the app owner reports a bug or questions a decision in the *rebuilt* app: respond with a plan to fix/change it, get explicit approval, implement the change, and then **update this requirements document** so it stays the single, current source of truth for how the app is supposed to behave.

**Git/deployment workflow (corrected)**: `qa` branch first, always. Commit and push to `qa` (→ the QA Vercel deployment) as the default result of ordinary approval ("go," "proceed," etc.) — `main` (→ Production) is **never** touched by that same approval. Promoting a change to `main`/Production requires the owner's own separate, explicit instruction to do so, every time — this matters most once real cutover (§10.2) has happened and Production has real users on it, but applies from now on, not just after cutover. (Corrected from earlier practice in this project, where every change was committed to `main` first and merged into `qa` second — backwards from this, and from what this section already said before that correction.)

**App version numbering (new)**: the app's own displayed version number (header corner, §2.1) is independent of Vercel's deployment history — it starts at **4.0**. Every time a change ships, you'll be prompted to decide the new version number: **+0.1 for a small change or fix** (e.g., 4.0 → 4.1), or **the next whole integer for a major release** (e.g., 4.x → 5.0). <span class="rev">The chosen version is recorded as a release in the console's **Release Notes** (§6.16, table `app_releases`, church-wide); every ministry's header shows the latest release's version (by release date), falling back to `app_settings.app_version` only if there are no releases.</span> This document is updated to note the change alongside its version number.
